# AFC 各版本横向对比（v2 / v3 / v4.2 / 线上）

同一批 6 个真实会话、同一套判定，只换算法版本。

## 3. 结论：谁更好

**没有全面胜出的版本，选谁取决于你要哪种保证。**

### v3 与 v2 几乎相同
固定预算下差异小于 0.5%（1,040 vs 1,036 字符，丢失数完全相同）。v3 修的是渲染层（问号、粘连标点），不改选句逻辑。所以 v2 与 v3 不是算法之争，是缺陷修复。

### v4.2 的强项和代价
- **强项**：0 坏标点、重复渲染减半；在 2,400 预算下与 v3 打平（都是 4/277）；
- **低预算下反而多丢**：1,300 预算时 v4.2 丢 28、v3 丢 22。差异集中在 [id] 类锚点（upstream_ssl_error 等），v4.2 的父句合并把技术标识符并进长句，存活判定在长句里匹配不到。这是合并渲染的副作用，不是选句变差；
- **代价**：autoBudget 让它平均输出 1,559 字符（比线上多 266），S3-B 单来源 2,523。

### 线上版本最弱
1,293 字符下丢 1.8%，还带 1 处坏标点。它的优势只是体积稳定可控。

## 4. 我的判断

**只问哪个算法更好：v4.2。**

在 2,400 预算这个保真区间，它和 v3 打平（4/277），但坏标点 0 对 6、重复渲染减半。低预算下的劣势来自合并渲染的判定假阴性，可以通过修 survives 对合并句的处理补掉。

**问能否直接替换上画布：不能。**

v4.2 的 autoBudget 输出平均 1,559、峰值 2,523/来源，三来源场景 7k+，比现在的 3.9k 翻倍。画布要的是体积可预测。

## 5. 推荐落地路径

不要整体替换，而是：

1. 采用 v3 的渲染修复（stripTail / joinParts），坏标点 6 降到 0、问号不再被改写；
2. 采用 v4.2 的父句去重，头部重复 18 降到 9；
3. 修 survives 对合并长句的 ID 匹配，把 v4.2 低预算下多丢的 6 个 [id] 锚点补回；
4. 保持线上的固定预算阶梯（800 到 2,400），不引入 autoBudget 双阈值。

这样能同时拿到：0 坏标点、重复减半、丢失不高于 1.8%、体积不变。
